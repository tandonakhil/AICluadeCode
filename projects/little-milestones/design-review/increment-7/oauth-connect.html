Increment 7 — F17 OAuth connect flow

Full-page redirect, not a popup — the same "this app hands you off to a real external page" pattern already legible to users from any standard web OAuth flow, and simpler/more transparent than a popup this app would have to babysit for blocked-popup failures. Clicking "Connect Google Photos" (settings-entry.html) navigates the browser to Google's own OAuth consent screen (shown below as a labeled mockup of Google's own UI, not something this app styles); Google redirects back to a fixed callback route on this app, which lands the caregiver back on Settings in one of the states below.

All three error states render the exact same calm-terracotta copy pattern already established for network/auth errors elsewhere in this app (Increment-1 fix #3, AuthScreen.tsx's parseErrorMessage convention) — --lm-terracotta-deep text, never --lm-danger (UXR-9), and never the raw HTTP/OAuth error code or provider error string. Cancel and failure both read as "try again," not as something the caregiver did wrong — a cancelled OAuth grant is a normal, expected outcome for an optional, off-by-default feature, not a fault state.

4. Disconnect — confirm dialog (desktop, centered per §5.6 split)

Disconnect Google Photos?

little-milestones will no longer have access to your Google Photos account. Photos you've already imported into a child's journey stay exactly as they are — nothing already imported is deleted.

Why not the destructive-red dialog: disconnecting revokes an access grant, it does not delete data (UXR-9 reserves --lm-danger for permanent data-loss confirmations only — profile/photo/memory/conversation delete). This reuses the lighter two-button confirm-dialog pattern already established for conversation delete (§9.1), styled with .lm-btn-secondary rather than a destructive variant, plus one explicit reassurance sentence that already- imported photos are unaffected, since "disconnect" could otherwise read ambiguously as "remove the photos too."
