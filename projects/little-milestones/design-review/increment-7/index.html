Increment 7 — Experience Design review F17 GOOGLE PHOTOS

Google Photos import: connect a caregiver's Google account (read-only, picker-based, off by default), pick specific photos in Google's own Picker UI, review before committing, import into the existing encrypt-at-rest photo pipeline. Source: FEATURES.md F17, approved 2026-07-11. Covers the four screens listed below at both mobile and desktop widths, per the standing responsive-web-app platform decision (PROJECT_CONTEXT.md Decisions Log, 2026-07-10, re-confirmed unbroken by any decision recorded since).

1. Settings entry 2. OAuth connect 3. Picker + review 4. Import results

Strategy summary

  • One-shot, not a persistent sync. The OAuth connection itself can persist (so a caregiver isn't re-consenting on every import), but no background sync, polling, or auto-import ever runs — every import is an explicit "open picker → pick → review → confirm" action, matching FEATURES.md's exact scope and the human's approved framing.
  • Scope minimization is visible in the copy, not just enforced server-side. Settings entry, the intro hand-off, and the review step all separately state read-only/picker-only/no-library-access, satisfying INDUSTRY_KB §2.2's third-party-disclosure expectation at more than one touchpoint.
  • Everything reused except one screen. Sheet-on-mobile/dialog- on-desktop split (§5.6), .lm-btn variants, calm-terracotta (never --lm-danger) error convention, the privacy-cue lock-glyph line (UXR-10), the photo-upload grid's 3→5 column precedent, the lighter two-button confirm dialog (not destructive-red) already used for conversation delete. The one genuine exception is Google's own Picker widget — flagged explicitly in picker-review.html, not silently fit into this app's component vocabulary.
  • Partial failure is shown, never swallowed. The results step lists real per-photo outcomes with a scoped retry, matching this KB's standing "shown honestly" instruction and the same discipline already applied to every other error surface in this app.

Flagged explicitly — new component vocabulary

Yes — one genuinely new UI surface. Google's own Photos Picker widget (launched via Google's Picker API) is not something this app can or should skin with its own tokens — it is the mechanism that makes scope-minimized, picker-based selection possible at all (this app deliberately does not build its own Google-library browsing view, since that would require exactly the library-wide access FEATURES.md rules out). Everything on either side of that widget — the intro hand-off sheet/dialog and the post-picker review step — is fully native to this app's existing storybook visual language and reuses established components. See picker-review.html's inline flag box for the full reasoning code-agent/Architecture should carry forward: this app treats the Picker as a black box it launches and receives a photo-id result from, not a surface it specifies pixel-by-pixel.

Everything else in this pass is existing component vocabulary — no new sheet/dialog pattern, no new button variant, no new error-color role, no new grid convention.
