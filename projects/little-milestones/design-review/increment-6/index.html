Increment 6 — Hardened auth suite (F12)

F12Design review for password reset, opt-in TOTP MFA, and session hardening — the four surfaces flagged by security-architect at SECURITY_KB.md §7's "what ui-ux-designer needs to design" list. Reuses existing .lm-sheet/.lm-dialog patterns, .lm-card, .lm-btn variants, and .lm-field/input styles throughout — no new component vocabulary is introduced anywhere in this increment.

1. Login + TOTP step 2. Forgot-password flow 3. Settings → Security

What this pass covers, and what it deliberately reuses vs. adds

  • Login additions — a "Forgot password?" quiet link under the password field; a second TOTP step (6-digit code, "use a recovery code instead" fallback) for enrolled accounts only, reached after a correct password via the existing generic-error convention (a wrong password never hints whether TOTP is enrolled).
  • Forgot-password flow — request → uniform "check your email" confirmation (byte-identical copy regardless of account existence, per SECURITY_KB §7.2's no-enumeration rule) → reset (new password + confirm) → success, routing to login. The reset page carries two functional (non-aesthetic) constraints: no third-party resource loads, and the raw token is stripped from the address bar via history.replaceState once read.
  • Settings → Security — a new card in the existing .lm-settings-grid 2-up desktop layout (§10.5): change-password, TOTP enrollment (password confirm → QR + manual secret fallback → verify → one-time recovery codes with a forced acknowledgment checkbox), TOTP disable (password + code), and an active-sessions list with per-session revoke + "log out everywhere." The old "no password reset yet" Privacy-card sentence is removed outright (§3 of the Settings file, before/after shown).
  • Reused, unchanged: the calm-terracotta error convention (UXR-9's single-red-surface rule is preserved — MFA disable/session-revoke dialogs are NOT styled destructive, since they're reversible settings changes, not permanent data loss); the 44px touch-target floor; focus-visible rings; the sheet-on-mobile / centered-dialog-on-desktop pattern already established for add-memory (§5.6) and photo-upload.
Decisions Log cross-check (per this role's completeness guardrail): the full PROJECT_CONTEXT.md Decisions Log was read before finalizing this pass, re-confirming the responsive-web-app platform decision — every screen in this increment is shown at both mobile (375px) and a genuine desktop width (sidebar nav / centered-narrow auth per §5.2's established split), not a stretched phone view. What this pass does NOT cover: the exact QR provisioning-URI generation, rate-limiter copy/behavior beyond what's shown, and any DesignSync push — no DesignSync tool was available in this session's tool set (same class of gap already on record at UX_KB §8.6/§9.3/§10.4); flagged here for whichever future pass has DesignSync access, additive only, no existing path to be touched.
