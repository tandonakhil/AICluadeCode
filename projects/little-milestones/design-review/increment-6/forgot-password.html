Forgot-password flow — request → uniform confirmation → reset → success

Four states, one flow, all reusing .lm-onboarding/ .lm-field/.lm-btn-primary/.lm-btn-quiet verbatim — no new visual language. Matches SECURITY_KB §7.2 exactly: the "check your email" copy is byte-identical whether or not the account exists (no enumeration), and the reset screen's functional constraints are called out below rather than only implied.

Functional requirement, not aesthetic (SECURITY_KB §7.2 / §1.7 point 5 reasoning applied here): the reset screen (state C) must load no third-party resources — no font CDN, no analytics, no external image — since the raw token sits in the URL and any outbound request could leak it via Referer. It must also strip the token from the visible address bar via history.replaceState once the token is read into memory, so the raw token doesn't linger in browser history/screenshots after the page has what it needs. Both are implementation requirements for code-agent, illustrated with an inline annotation on state C below, not new visual elements.

Copy identity note (not a second visual state)
This exact screen renders whether maya.parent@example.com has an account, doesn't have an account, or the account exists but the send itself failed server-side (SECURITY_KB §7.2: "always returns the same generic 202... for known email, unknown email, AND send failure"). The email address shown back to the user here is simply what they typed into the request field — echoing user-supplied input is not an enumeration leak, since it reveals nothing the browser didn't already know. No branch in this screen's markup may vary by account existence.

Address-bar annotation (implementation note, not a visual element): the URL this page loads at, e.g. littlemilestones.app/reset-password?token=aB3k9..., must be replaced via history.replaceState(null, "", "/reset-password") immediately after the token is read into component state — before this form renders, not after submit — so the raw token never sits visibly in the address bar, browser history, or a screen-share/screenshot taken while this page is open. The page itself: no <link> to any external font/CSS, no analytics snippet, no third-party embed of any kind — same discipline SECURITY_KB §1.7 point 5 already required of the unsubscribe confirmation page, applied here because this token is materially more sensitive (a password-reset capability, not an opt-out toggle).
