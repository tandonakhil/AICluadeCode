Photo Personalization (revision 4) NEW

Human feedback: "once a parent uploads their kid's pics we should show pictures in general theme so it looks personal. if no picture then default theme." This section shows a decorative photo-derived accent layer applied to select surfaces (hero gradients, card accent borders, background wash, switcher avatar ring), the same screen in the unmodified default theme for direct contrast, and the child switcher previewing two independent per-child accents. Full design rationale, the AA-contrast guarantee for arbitrary photos, and the hard exclusion of the slate/red/text tokens are in UX_KB.md §6.

Personalized: hero/header gradients, card accent borders, top background wash, child-switcher avatar ring.   Never personalized: the slate pediatrician-note surface (R1/R2), the single red destructive color, all body/UI text and its contrast ratios, primary action color (terracotta stays the one tappable-affordance color everywhere).   AA guarantee: extracted accents are clamped to safe lightness/saturation bands, a fixed-opacity dark scrim (independent of hue) sits behind any white headline text, and an automated pre-render contrast check falls back to the default theme for that surface if a fixture photo would still fail — personalization degrades to default, never to a contrast violation.   Default state: no photo = the complete, unmodified rev-2 theme, not a gray placeholder.   Multi-child: each profile's accent is derived from its own photo only — never shared across children.

Increment 4 — Profile Avatars, Journey Lightbox, Journey Gallery F14 / F15 / F16

Human-approved post-MVP bundle (2026-07-12, FEATURES.md's "Post-MVP roadmap" section) — three backlog items designed as one coherent pass since all three touch the same Journey screen and the same profile-photo display: F14 shows the profile's real photo as an avatar in the switcher, Today header, and Journey header (falling back to the existing colored identity dot when there's no photo); F15 lets a caregiver click any Journey photo to expand it full-resolution in an on-screen overlay instead of navigating away; F16 adds a toggleable dense grid alternative to the chronological river, whose tiles open the exact same lightbox F15 designed. All three preview files below use the app's real fixed --lm-* tokens from dev/frontend/app/globals.css, copied verbatim, and are shown at both mobile and desktop widths. Full design intent, coverage notes, and the flagged backend/data gap: UX_KB.md §8.

F14 fallback contract: a photo, when one exists, replaces the colored dot everywhere; the dot itself is completely unchanged as the no-photo state — same mechanism, three sizes (32px switcher, 44px Today, 56px Journey).   F15 dismiss: visible close button, Escape key, and backdrop click — never a tap on the image itself. Focus moves to the close control on open and returns to the exact photo that was clicked on close.   F15/F16 shared component: one <Lightbox>, two seed lists — the timeline scopes prev/next to one memory's photos, the gallery scopes prev/next to every photo on the profile.   F16 view state: client-only for this pass, defaults to Timeline, never both views rendered at once.
Flagged for human/Architecture attention: displaying a real profile-photo avatar (F14) needs one small additive backend surface not currently exposed — a nullable avatar_photo_id on the Profile response (or equivalent), sourced the same way as the existing "last-uploaded-wins" accent-extraction rule. No new storage, table, or encryption surface; full reasoning in the implementation note inside avatar-treatment.html below and in UX_KB.md §8.4. Also flagged: this pass could not push to DesignSync (no tool access in this environment) — see UX_KB.md §8.6.
