Increment 5 — Chat History Browsing (mobile), F13 part 1

A new History icon (clock glyph, 2px-stroke line icon per §1.2) sits in the age-context strip next to the existing corrected-age "i" affordance. Tapping it opens a bottom sheet — the same .lm-sheet-backdrop/ .lm-sheet grabber-card component already shipped for AddMemoryForm and the profile switcher — listing past conversations for the current child, newest first.

Design calls made here (pure UX, not Architecture's)

  • Discrete conversations, not one continuous log. Matches this app's existing "chaptered" idiom (Journey's chapter markers) better than an infinite scroll — a parent scanning for "that time we talked about walking" benefits from date-grouped chunks, not one giant transcript.
  • Row anatomy: relative date ("Today," "Yesterday," "Tue, Jul 8"), a literal snippet of the parent's own first message in that conversation (never an AI-generated summary — no new LLM-origination surface), and a message-count badge.
  • Continuity default: opening Chat resumes the most recent conversation automatically (like returning to an open notebook) — the dynamic suggestion chips (see suggested-prompts.html) only appear when the open conversation has zero messages, exactly the same trigger condition as today, just scoped per-conversation instead of per-app-load.
  • Delete = the existing photo/memory-delete dialog pattern (two-button confirm, no typed name) — not the heavier typed-confirmation profile-delete pattern, since deleting one conversation is lower-stakes than deleting a child's entire profile/photos/memories in one action. Still the single red surface (UXR-9); copy states permanence plainly.
  • No cap on how far back a caregiver can browse from the UX side — same "kept until the caregiver deletes it" retention discipline as memories/photos. Whether the list paginates/infinite-scrolls at high volume is a performance/implementation question, not a visual one (flagged below).

Flagged for Architecture (real schema/behavior decisions, not decided here)

  • Conversation-boundary rule. Design intent: a new conversation starts either (a) explicitly, via "+ New conversation," or (b) implicitly, when a caregiver opens Chat and the most recent conversation is "stale" — but the exact staleness threshold (e.g. a calendar-day boundary vs. an N-hour inactivity gap) is Architecture's call, not specified here.
  • Snippet storage. Whether the row's snippet is a stored column (denormalized at write time) or computed on read from the first stored message is an implementation detail with no UX-visible difference — Architecture's call.
  • Pagination / list-size performance once a family has dozens of conversations — not designed here; UX only specifies the row anatomy and that nothing is hidden by an artificial cap.
  • Real open question, not just Architecture's — needs explicit confirmation (Architecture + human): does chat history scope per-profile (shared across all caregivers on that child, matching how memories/ photos already work under F10) or per-(profile, caregiver)? Default recommendation below leans per-profile for consistency with the existing memory/photo scoping precedent, but chat is different from a logged memory — a caregiver's own worried 2am questions are more personal than a milestone entry, and showing them to a co-caregiver by default is a real privacy call this design does not make unilaterally.

Default recommendation (not a decision): per-profile, shared across caregivers — consistent with existing F10 scoping for every other data type in this app — unless the human/ Architecture wants a different, more private default for chat specifically.
