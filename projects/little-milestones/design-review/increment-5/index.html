Open Questions Summary — what's settled vs. what Architecture must decide

Settled here (pure UX/visual, no further design work needed): discrete per-conversation grouping (not one infinite log); row anatomy (relative date, literal-snippet, message count); resume-most-recent default; delete = the existing two-button confirm-dialog pattern (not typed-confirmation); the fixed suggested-prompt template library (T1–T4) and its R1/R2-compliant copy; the History icon placement, the mobile sheet, and the desktop rail's placement/behavior.
Flagged for Architecture (real schema/implementation decisions):
  1. Exact chat_sessions/chat_messages schema shape (not prescribed here).
  2. Conversation-boundary rule — the precise staleness threshold that starts a new conversation implicitly.
  3. Whether the conversation-list snippet is stored or computed on read.
  4. Pagination/performance for a caregiver with many stored conversations.
  5. Whether suggested-prompt templating is a new backend endpoint (recommended, mirrors /activities/ /products) or computed client-side from already-fetched data.
  6. Needs explicit Architecture + human confirmation, not just Architecture's: does chat history scope per-profile (shared across caregivers, matching F10's existing memory/photo precedent — this design's default recommendation) or per-(profile, caregiver)? Chat content is more personal than a logged memory, so this default should be confirmed rather than inherited silently.
