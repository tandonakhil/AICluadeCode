Increment 5 — Dynamic, Age/History-Aware Suggested Prompts (F13, part 2)

Replaces ChatScreen.tsx's static SUGGESTION_CHIPS constant (3 fixed generic strings) with chips assembled from a small, fixed, non-LLM template library — filled only with curated data (milestones_cdc2022.json bucket content already served via /profiles/{id}/activities) and the profile's own logged Memory.milestone_tag values. No chip copy is ever model-generated. Empty-state only (messages.length === 0), exactly where the current chips already render.

Fixed template library (design-owned copy, same discipline as F9's catalog-only product cards)

Selection rule (design intent, exact code seam left to Architecture/code-agent): show 3 chips — T1 + T2 + (T3 if a tagged memory exists, else a T4 pick). Newborn/out-of-range mode: T1/T2 have no meaningful bucket to reference, so chips fall back to 2–3 T4 picks only, matching the existing out-of-range context-strip tone already in ChatScreen.tsx ("milestone content covers birth to 3, but ask me about activities anytime").

Flagged for Architecture (not decided here)

Whether this templating runs as a new small backend endpoint (e.g. GET /profiles/{id}/suggested_prompts, mirroring the existing /activities//products pattern — same curated-table-plus-template-function shape, zero LLM code path) or is computed client-side from data the frontend already fetches (ageInfo from getActivities, plus a new/reused memories fetch) is an implementation-symmetry decision, not a visual one. Recommendation: a backend endpoint, for the same reason F9's catalog filtering is server-side — keeps "what data can produce a chip" centralized and testable in one place rather than duplicated into the frontend. Not prescribing further; Architecture's call.
