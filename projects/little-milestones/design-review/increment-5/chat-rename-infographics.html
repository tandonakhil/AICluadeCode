Increment 5 addendum — Renaming "Chat" + Infographic Elements

Two follow-up requests from the human's approval of §9's shared-per-profile chat-history design: (1) rename the Chat page to something that communicates the actual value ("age-aware guidance, grounded in CDC data, tied to their specific child") rather than "a chat box"; (2) make the page more visually engaging with infographic-style elements. Both are shown here composed with the already-approved history rail and suggested prompts (suggested-prompts.html, chat-history-desktop.html, chat-history-mobile.html) so this reads as one coherent screen, not a bolt-on. Read against RESPONSIBLE_AI_KB.md §3.1/§3.4 (R1) — every element below was checked against the "no expected-vs-actual visual, no progress-bar-against-norms" boundary.

1. The rename

Recommendation: rename "Chat" → "Ask"

OptionVerdictReasoning
"Consult" (human's first suggestion) Not recommended — flagged risk "Consult" reads as "seek a professional/medical consultation." That's in direct tension with RESPONSIBLE_AI_KB §3.2's refusal boundary and the disclaimer's own load-bearing sentence ("not medical advice or a developmental screening tool," §1.10) and the trust posture that the assistant "has no persona pretending to be a clinician" (§1.6c). A tab labeled "Consult" sets an expectation the product then has to actively walk back in nearly every reply. The value this page provides (age-aware, CDC-grounded, child-specific guidance) is real — but "Consult" borrows medical-authority language to say it, which is the wrong trade for a product whose R1/R2 boundaries exist specifically to avoid sounding like a clinician.
"Discuss" (human's second suggestion) Safe, but weak No R1/R2 risk — "discuss" is neutral and warm. But it's barely more purposeful than "Chat": it names the *mechanism* (a back-and-forth) rather than the *value* (guidance suited to this child, right now). It would be an acceptable fallback if "Ask" is rejected, but doesn't clear the bar the human set ("communicate what the user gets out of the page").
"Ask" (this proposal) Recommended Already the verb this product uses everywhere the chat is referenced: the onboarding CTA chip ("Ask anything — try: what does a typical {age}-month-old enjoy?", §1.5 Flow 1a), the empty-state hint ("Ask anything, or try one of these:"), and the composer placeholder ("Ask about {Name}...") all already say "ask," not "chat." Renaming the tab to match is zero new copy vocabulary — it closes a gap between what the app already calls this action and what the nav label calls the destination. "Ask" is also one syllable (fits the existing one-word tab-bar convention: Today · Journey · Add) and, paired with the new stage-snapshot card below, the page itself now visibly demonstrates the "age-aware, tied to your child" value the human wants communicated — the single nav word doesn't have to carry that whole promise alone.

2. Infographic elements — the "stage snapshot" card + domain iconography

Concept

A new .lm-stage-card renders in the same empty-state slot as the suggested prompts (messages.length === 0 for the open conversation) — enriching the moment a parent opens a fresh conversation, without adding permanent chrome to an active message thread. It bundles three things the human asked for in one cohesive, non-comparison visual:

ElementWhat it showsData source (no new LLM content)
Illustrated identity strip The child's avatar (F14, §8.1 — photo or identity-dot fallback) + name + age, styled with the serif display face used on the Journey header (§1.6b), so the card visually echoes the journey's already-approved "storybook" register rather than inventing a new one. Existing profile/age data
Elapsed-time micro-line "342 days of Maya's story so far ✦" — a small, quiet text line under the name, reusing the Journey header's exact elapsed-time phrasing pattern ("412 days of Maya — 23 moments so far," §1.6b) rather than a numeric ring, dial, or segmented bar. Existing age computation (same source as the age strip)
Current-stage sentence "This month, many little ones are exploring balance, first words, and connection." — one plain sentence built from the current bucket's domain tags. Identical source and template discipline as §9.2's T1 chip (milestones_cdc2022.json bucket domain field via the same fixed domain→phrase map) — literally the same data, rendered as a sentence instead of a chip. No new content-origination surface.
Domain icon chips A row of small tappable pill chips — one per milestone domain (movement, language, social, cognitive) — each with a 2px-stroke line icon. Tapping one asks the same T1 template scoped to that domain ("Fun ways to build {domain_phrase} right now"). Same T1 template/domain map, §9.2 — a visual entry point into content that already exists, not new copy.

Why this stays inside R1's boundary (re-verified against RESPONSIBLE_AI_KB §3.1/§3.4)

  • No expected-vs-actual visual. Nothing on the card compares Maya to a norm, a percentile, or another child. The domain chips are activity-framing entry points ("build X right now"), the same register as the existing "Ideas for rainy-day play" chip and Today's activity cards — never a checklist of what Maya has or hasn't done.
  • No progress-bar-against-norms. The elapsed-time line is deliberately text, not a ring, dial, or fill-bar — a segmented/partial-fill visual was considered and rejected explicitly: even an "elapsed time" ring risks being misread as "percent of development complete" the moment it has any implied ceiling. Journey's own header already solved this the same way (a phrase, not a bar) — this card reuses that exact solved pattern rather than inventing a riskier one.
  • No checklist-with-weight on the domain chips. All four domain chips render every time, at identical visual weight — no filled/empty state, no checkmark, no graying-out of domains "not yet reached." Graying out or checking off domains was considered and rejected: it would visually imply "areas covered vs. not," which is exactly the comparison framing R1 bans. The only ordering signal is that the current bucket's most relevant domain(s) sort first (a convenience, not a status — see the "primary" chip style below, which is a placement/ tint distinction only, never a completion state).
  • No new content-origination surface. Every string on the card (the stage sentence, the domain phrases, the chip templates) is sourced from the same fixed, non-LLM template library already specified and cleared in §9.2 — this card is a new visual arrangement of already-approved data, not a new place the model can originate framing.
