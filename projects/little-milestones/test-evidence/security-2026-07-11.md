## Check 1 — argon2id used for password hashing (not a weaker default)

**File:** `dev/backend/app/auth.py`

```python
_pwd_context = CryptContext(schemes=["argon2"], deprecated="auto")
```

**Static finding:** `passlib`'s `argon2` handler (`passlib.handlers.argon2`)
defaults to `type="ID"` (argon2**id**) as of passlib ≥1.7.2, provided
`argon2-cffi` is installed as the backend — which it is here:
`pyproject.toml` declares `passlib[argon2]>=1.7`, and the `[argon2]` extra
is exactly what pulls in `argon2-cffi`. `passlib` does not default the
`argon2` handler to `argon2i` or `argon2d` in this version range; nothing in
`auth.py` overrides `type` to a weaker variant. `hash_password`/
`verify_password` are thin, faithful wrappers (`_pwd_context.hash` /
`_pwd_context.verify`) with no shortcuts.

**Not independently executed this run:** I could not actually run
`hash_password("test1234")` and inspect the resulting hash string's `$argon2id$`
prefix (which would be the fully conclusive check — passlib/argon2 hash
strings self-identify their variant) because no exec tool was available.
Static inspection of the import (`passlib.context.CryptContext`,
`schemes=["argon2"]`) plus `pyproject.toml`'s declared dependency
(`passlib[argon2]`) is consistent with argon2id, but this is inference from
documented library defaults, not an observed hash string.

**Result: PASS (static), with the roundtrip-execution portion of the check
UNVERIFIED — recommend re-running with exec access before this is treated as
fully closed.**

## Check 2 — session tokens hashed before storage, not plaintext in SQLite

**Files:** `dev/backend/app/db.py` (schema), `dev/backend/app/auth.py`
(current Increment-1 logic).

**Finding:**
- Schema (`db.py` `SCHEMA` constant): `sessions` table has a `token_hash`
  column as its primary key — there is no `token` (raw) column in the
  schema at all. This matches SECURITY_KB §1.1's design (`{token_hash,
  user_id, created_at, expires_at}`) exactly.
- **No code path writes to the `sessions` table in Increment 1.** `auth.py`
  contains no `INSERT INTO sessions` anywhere; `get_current_family`'s
  Increment-1 body only reads/seeds the `families` table, never touches
  `sessions`. No `routes/auth.py` file exists yet (confirmed — file read
  attempt returned "does not exist"), and `main.py` mounts only `chat` and
  `profiles` routers, not `auth`. So there is no live signup/login flow this
  increment that could write a plaintext token even if it wanted to — the
  question "is a token stored in plaintext" has no code path to answer
  wrongly yet, because no session-issuing code exists yet.
- Consistent with `auth.py`'s own module docstring: "Password hashing is
  wired up now... it is not reachable from any route yet, since no
  signup/login route exists before Increment 3." Session issuance is
  further out than password hashing — not even a helper function exists for
  it yet in this increment (only the storage column is pre-declared in the
  schema, per ARCHITECTURE_KB §3's "lay down the schema for later
  increments' entities too").

**Result: PASS.** No plaintext-token storage exists, because no session
storage code exists yet — the schema itself is already hash-only-shaped
(`token_hash` PK, no raw-token column), so there is no design defect waiting
to be activated either.

## Check 4 — no unauthenticated write-capable route exists that shouldn't, and `get_current_family` stub defaults safely

**Files:** `dev/backend/app/main.py`, `dev/backend/app/routes/profiles.py`,
`dev/backend/app/routes/chat.py`, `dev/backend/app/auth.py`.

- `main.py` mounts exactly two routers this increment: `profiles` and
  `chat`. No `auth` router file exists at all
  (`dev/backend/app/routes/auth.py` — read attempt confirms: file does not
  exist). So there is no signup/login/session route reachable yet, and
  therefore nothing yet depends on `get_current_family`'s eventual
  Increment-3 real-session behavior for security — every currently-mounted
  route (`POST/GET/DELETE /profiles*`, `POST /chat`) depends on
  `get_current_family`, which is uniformly the Increment-1 stub.
- **Every route that writes** (`POST /profiles`, `DELETE /profiles/{id}`)
  does go through `get_current_family` as a `Depends()` — there is no route
  bypassing the dependency. This matches ARCHITECTURE_KB §2's stated
  contract ("present on every route from Increment 1").
- **Does the stub "accidentally expose one family's data to another"?
  No — and the reason is structural, not just "it happens to work":**
  `get_current_family`'s Increment-1 body always returns
  `Family(id=DEFAULT_FAMILY_ID)` (`DEFAULT_FAMILY_ID = 1`), and there is
  **no code path anywhere in the currently-mounted routes that can create a
  second `families` row** — no signup route, no invite-acceptance route, no
  admin route. `families` only ever gets a row via `db.py`'s
  `init_db()` seed (`INSERT OR IGNORE INTO families (id) VALUES (1)`) and
  `get_current_family`'s own defensive re-seed of the same id. So at this
  increment there is structurally exactly one family in the system, and
  every profile/memory/chat request is scoped to it — "expose family A's
  data to family B" has no B to expose to yet. This is a stronger guarantee
  than "the stub happens to default safely"; it's "there is no second
  tenant reachable by any mounted route," which is what actually matters
  for this increment's risk.
- **Caveat, stated for the record, not a finding against this increment:**
  this safety property is contingent on `auth`/invite routes staying
  unmounted. The moment Increment 3 mounts a real signup/invite route that
  can create a second family or a second user, `get_current_family`'s body
  must be swapped to the real session-resolving implementation in the same
  change — ARCHITECTURE_KB §2 already commits to this ("Increment 3
  replaces the function body only... verified as an architecture-suite
  contract test") and this is the correct point to re-run this exact check
  (cross-family 404, PLAN §7-J34) as a live behavioral test, not just a
  structural one.

**Result: PASS.**
