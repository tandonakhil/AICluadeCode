What you are looking at

Two additions, shown together because they're both about giving an analyst a useful next question, not about changing what the corpus contains or what the wall permits:

  • The session is always MidWestUtilities. Not a login screen — the human's own decision, recorded: "assume the user is a MidWest utility logged in." What the app bar shows changed from a generic role label to a named utility, and a persona picker sits underneath it that biases which recommended questions surface. Switching persona never changes the wall, the corpus, or what a question can retrieve — only which starting questions are suggested.
  • Two follow-up suggestions appear under every answer and refusal, built from the corpus index — not the model, same rule the refusal screen's alternatives already follow (ASM-UX-8 as narrowed). Each is a real, individually citable question. Comparisons are always to a named peer case with its own citation — never an average or a benchmark (ASM-14 holds).

Assumptions, stated plainly

  • Persona changes suggestions only. It is stored client-side for this session (no new session-role concept, no new wall boundary) — a decision recorded so it isn't mistaken for an access-control feature later.
  • Follow-ups are generated from the corpus index against the case just answered — the same pattern as a refusal's alternatives, and bound by the same rule: never relax the one dimension that made this answer specific (asking a laxer version of the same question), and never propose an aggregate.
  • Recommended-question sets are static per persona for MVP, not generated per-question by a model call — cheap, deterministic, and avoids inventing a fourth live-model call site under time pressure. A future pass could make them corpus-derived the same way follow-ups are.
